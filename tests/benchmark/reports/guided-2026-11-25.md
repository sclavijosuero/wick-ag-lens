# Guided benchmark report: agent-browser vs Playwright MCP (2026-11-25)

Status: five runs per approach (10 runs, 2026-11-25). The numbers are indicative, not statistical. A rerun with automatic approval, to get clean durations for B, was attempted and could not be done (section 7); the durations of B below are still affected by manual approvals.

## 1. What was measured

The benchmark measures what it costs an LLM agent to drive a browser through a fixed user journey when the agent is given the journey in plain words. It compares two ways of driving the browser:

- **Approach A:** the agent browses with the `agent-browser` CLI.
- **Approach B:** the agent browses with the Playwright MCP tools.

In both approaches the accessibility audit is done by the same tool, the wick-ag-lens CLI. The agent's job is to discover the page's selectors, sign in, assemble one wick-ag-lens command with the journey steps, run it, and report the result.

Measured per run: total tokens, tool calls and wall-clock duration of the agent, plus the correctness of the final report against an answer key.

## 2. How the benchmark works

1. **Page under test.** A dedicated mid-size commerce page, [`tests/fixtures/pages/bench-shop.html`](../../fixtures/pages/bench-shop.html) (sign-in page: [`bench-login.html`](../../fixtures/pages/bench-login.html)), served by [`tests/fixtures/server.js`](../../fixtures/server.js) on `http://127.0.0.1:4470`. The journey and audit list are defined in [`tests/benchmark/journey.js`](../journey.js) and the answer key in [`tests/benchmark/reference.js`](../reference.js); the agents were not given access to any of these. It has deliberate accessibility problems that appear and disappear as the user interacts. It sits behind a login (`/bench-login.html`, user `jdoe`, password `Admin+123`); the shop page redirects to the sign-in page when there is no session.
2. **Journey.** 15 user actions (section 4). Together with the page load, this gives 16 audited states.
3. **Audits.** Exactly 30 audits are requested: 15 violation audits (`v-*`) and 15 structural audits (`i-*`, one of them `i-focus-order`).
   **WCAG versions and levels: no filter was applied.** The prompts did not pass `--wcag-version` or `--wcag-level`, so wick-ag-lens ran with its defaults: all supported WCAG versions (2.0, 2.1 and 2.2) and all conformance levels (A, AA and AAA) are evaluated, and rules whose legends have several levels (for example text contrast) report their AAA results as well. The answer key was generated under the same default. A run restricted to the recommended scope (versions 2.0 and 2.1, levels A and AA) would report fewer findings, so its counts are not comparable with these.
4. **Guided mode.** The agent receives the journey as plain-language actions and is **not** given any CSS selector. It must discover them by browsing the running page. Discovery is part of what is measured.
5. **Independence.** Each run is a separate subagent with its own context, its own browser session and its own scratch folder. The runs were executed one after the other, never in parallel, and neither agent received the other's output or the answer key.
6. **No-peeking rule.** Both prompts forbid reading the page's source, `tests/`, `samples/`, `extension/`, or any file that mentions the shop or its journey. Before the final runs a first attempt of run A was stopped and restarted after this rule was added. The numbers below come only from the restarted run.
7. **Audit execution.** wick-ag-lens opens its own browser, signs in, performs the steps one by one and audits the page after load and after every step. It reports only the difference from the previous state (new findings and resolved findings).
8. **Scoring (no LLM, no tokens).** `tests/benchmark/score.js` compares the agent's table with the answer key (`tests/benchmark/reference.js`, generated from real runs of the same journey) and checks the real output file of the agent's own command. It also compares the agent's table with that output file.
9. **Output size.** The audit writes a JSON file of about 421 KB per run (findings per step, focus path, rule dictionary); see Annex C. The agents never read it whole.
10. **Metrics source.** Tokens, tool uses and duration are taken from each subagent's completion notification. They include the fixed overhead of the subagent (system prompt and tool definitions) and the cost of re-reading the context on every tool call, so they measure the whole run, not only the browsing.

## 3. Model used

Both runs were executed by subagents that inherited the session's model: **Claude Sonnet 5.5** (`claude-sonnet-5-5`). No model override was set on either run, so the two approaches ran on the same model.

### 4.1 Common to both approaches (verbatim)

The shared prompt is stored in `tests/benchmark/prompts/guided-common.md`. Placeholders: `{BASE_URL}` = `http://127.0.0.1:4470`, `{SCRATCH_DIR}` = a per-run scratch folder (`bench2-a`, `bench2-b`), `{TOOLS}` = the section in 4.2 or 4.3.

Contents of the shared prompt:

- **Role and rules:** one run of a benchmark; stay on the tool path stated in TOOLS; do not edit repository files; do not read repository files other than what the wick-ag-lens command needs; selectors must be discovered only by browsing the running page; do not open the page's source, `tests/`, `samples/`, `extension/` or any file that mentions the shop or its journey.
- **Task:** the shop URL, the shop page URL (`/app/bench-shop.html`), the fact that it needs a login, the sign-in page URL and the demo credentials.
- **Journey, in plain words, no selectors:**
  1. Open the "shop by category" panel with the menu (hamburger) button in the header.
  2. Hover the "Shop" item of the main navigation (it shows a menu).
  3. Close the category panel with the same menu button.
  4. Type "tent" in the search box.
  5. Press Enter in the search box.
  6. Sort the results by price, low to high.
  7. Open the "Brand" filter in the sidebar.
  8. Open the quick view of the first product in the list.
  9. In the quick view, enter 0 as the quantity.
  10. Click "Add to cart" in the quick view.
  11. Wait for the notification that confirms the product was added (it appears a few seconds after the click).
  12. Open the cart with the cart icon in the header.
  13. Click "Checkout" in the cart.
  14. In the checkout form, type "not-an-email" in the Email field.
  15. Press the Escape key to close the cart.
- **WCAG scope:** not mentioned in the prompt. The agents were not told about `--wcag-version` or `--wcag-level`, and neither used them, so all versions and levels were evaluated (section 2, item 3).
- **The 30 audits** (the exact `--audits` list): `v-missing-alt, v-empty-buttons, v-empty-links, v-generic-link, v-unlabeled-inputs, v-placeholder-label, v-aria-invalid, v-broken-aria-ref, v-duplicate-id, v-heading-errors, v-unfocusable, v-tabindex, v-aria-hidden-focus, v-text-contrast, v-svg-accessible, i-focus-order, i-landmarks, i-valid-headings, i-image-alts, i-aria-roles, i-accessible-name, i-aria-expanded, i-aria-controls, i-aria-live, i-required-fields, i-field-desc, i-fieldsets, i-touch-targets, i-tabindex-all, i-aria-pressed`.
- **Command and step grammar:** `node index.js audit "<page url>" --audits "<list>" --step "action::target[::value]" ... <login options>`, run from `cli/`. Actions: `click`, `hover`, `fill`, `select`, `press` (with `active` for the focused element), `wait` (selector or milliseconds). One `--step` per journey action, in order.
- **Output handling:** the JSON output is large, redirect it to a file, never print it whole, read only a compact summary.
- **Final answer format:** a table with one row for step 0 (page load) and one per journey step, columns `Step | Action | New (audit:elements) | Resolved (audit:elements)`, then a `STEPS:` line and a `Tool calls:` line.

The page's source, the answer key and the journey definition with selectors were not provided to either agent.

- **The audit command takes the same time in both approaches**, about 43 s. A1's 139 s is because its agent ran the audit command more than once after failed attempts.

## 6. Interpretation of the numbers

Section 5.3 is measured. This section separates what the measurements support from what they do not.

- **Supported:** B uses more tokens than A in this journey (+53% on average, in all five pairs). The extra is input only: output is the same. B makes 17% more model calls, and its context per call is about 40% larger.
- **Supported:** duration does not separate the approaches in five runs (the ranges overlap, medians 236 s and 212 s). The time is spent in different places (section 5.7): A spends more in browsing tool calls (about 137 s against 61 s), B more in model turns (about 98 s against 57 s), and the audit command takes the same 43 s in both. A's slowest run (A1) included failed attempts (a first `state save` with the wrong fields, wrong selectors, a premature `close`) and repeated audit runs; B's slowest (B2) had two late tool results (84 s and 109 s) of unknown cause.
- **Plausible, not measured:** that B's larger context comes from its tool definitions (loaded with ToolSearch and kept in the context) and from the page snapshot that most Playwright MCP actions return, while agent-browser returns a snapshot only when asked and only for interactive elements (Annex A explains the mechanisms). The sizes of the individual tool results were not extracted.
- **Plausible, not measured:** that the agent-browser handoff costs extra calls (`state save`, then `-a`) while B passes credentials to wick-ag-lens directly. A's runs used between 11 and 22 tool uses, B's between 25 and 32, so the handoff did not make A use more calls overall.
- **Not covered:** how the tools behave when the agent has to decide the steps (open-ended mode), other pages, other models.

## 7. Limitations and changes during the benchmark

- **Five runs per approach.** The token ordering is consistent, but five runs are not a statistical sample; the duration difference is within the variation.
- **LLM variation.** Agents chose different selectors and different numbers of tool calls from run to run, so the totals include their discovery and their mistakes. That is part of what is measured.
- **One model, one page, guided mode only.** The agents are told the actions; they do not decide them.
- **Durations of approach B include human approval waits.** The person running the benchmark had to accept the Playwright MCP tool prompts during the runs (the permission rule was not active in the session), so every B duration is an upper bound on what B takes with automatic approval. The effect is on time only: tokens and tool calls are not affected, except that B4's long wait outlived the cache lifetime and raised its cache-write tokens (142,071 against 78,000 to 94,000 in the other B runs). B's browsing time is about 61 s per run on average, so removing the waits can reduce a B run by at most that much; the size of the real effect was not measured. The agent-browser commands (approach A) did not ask for approval, according to the person running the benchmark, so A's durations are not inflated. This means the comparison is biased against B: with automatic approval B would be faster than the figures show, by at most about 61 s per run (its mean browsing time) and probably by less. A clean duration comparison needs a rerun with automatic approval for both approaches. **This was attempted and failed:** an allow rule for all Playwright MCP tools (`mcp__playwright__*`, in the user settings, besides the project rule `mcp__playwright`) was shown as active in the permission list of the session, and the organization's managed settings do not restrict user rules, but the extension still asked for approval on `browser_navigate`, both for a subagent and for the main session (a test call to `about:blank`). The rerun was therefore not made, and no new run was added: the results in this report are the five runs per approach already described. The cause of the prompt was not identified.
- **Cost is an estimate** with one assumed price (cache write); see section 5.4.
- **One contaminated run (A2)** and **one stalled run (B4)**, described in section 5.1. Both are kept in the tables; B4's stall (a permission prompt that waited for a person) is left out of the duration statistics. Unattended runs need the Playwright MCP tools allowed in the permission settings before the session starts; the other B runs may also have had short waits for the same reason (B2's two late results are unexplained).
- **Two product fixes were made between runs 3 and 4, at the request of the user**, after a review of the product found two issues: the text-contrast audit declared its severity as `CRITICAL` (now `Critical`, like the other audits), and the step diff identified findings by selector and text only, so elements sharing a selector (such as duplicate ids) were not counted one by one when their number changed between steps (now each occurrence is counted). The journey does not trigger the second case: the answer key regenerated with the fixed tool is identical to the earlier one, which is why the five runs can be compared. A fourth run of A that had already started when the fixes were made was stopped and run again; its tokens are not counted.
- **Some duplicate-id counts** in the key (for example `v-duplicate-id` at the page load and in the quick view) are the counts the tool reports; they follow the tool's own definition of an element.

## 8. Reproduction

- Start the fixture server: `FIXTURE_PORT=4470 node tests/fixtures/server.js`.
- Render the prompt from `tests/benchmark/prompts/` (shared prompt plus one tools file), substituting the placeholders in 4.1.
- Run the prompt as a fresh subagent (no memory of previous runs), one approach at a time.
- Score: `node tests/benchmark/score.js <agent-answer.md> <wick-output.json>`.

## Annex A. What each component does and where tokens are spent

### A.1 Who uses the model

Only one component in this benchmark uses a language model: **the agent** (here Claude Sonnet 5.5). Everything else is ordinary software that runs deterministically and costs no tokens by itself:

| Component | Is a model used? | What it does |
|---|---|---|
| The agent (subagent) | **Yes**, this is the only place | Reads text, decides what to do next, chooses selectors, writes commands, writes the final table |
| Playwright MCP server | No | Exposes browser actions as tools; runs Playwright; returns text (often a page snapshot) |
| agent-browser CLI | No | Command-line browser controller; runs commands typed by the agent; prints text |
| wick-ag-lens CLI (and its MCP server) | No | Opens its own browser, signs in, performs the steps, runs the audits, writes the JSON |
| `score.js` and the Playwright tests of the benchmark | No | Compare outputs with the answer key |

The tools never reason about the page. They only act and report. All interpretation, such as "this button is the Brand filter" or "the first product is `#qv-1`", is done by the agent.

### A.2 When tokens are spent

Tokens are spent only when the agent's model is called. Each model call consumes:

1. **Input tokens:** the whole conversation so far (the prompt, the tool definitions, every earlier tool call and every earlier tool result). This is re-read on every call, so a large result added early is paid for again on every later call.
2. **Output tokens:** what the agent writes in that call (its reasoning, the command or tool call, the final answer).

A tool run itself (a click, a snapshot, an audit) costs no tokens. It costs tokens only through what it **returns**, because the result becomes part of the conversation the model reads on its next call.

The subagent total reported in this document (`subagent_tokens`) is the sum over the whole run. It also includes the fixed overhead of a subagent (system prompt and the tool definitions available to it).

### A.3 How each approach talks to the model

**Approach A: agent-browser (CLI through the Bash tool)**

1. The agent calls its general Bash tool with a command, for example `npx --no-install agent-browser snapshot -i`.
2. agent-browser runs the command against its browser session and prints text to stdout. With `snapshot -i` the text lists the interactive elements with references such as `@e3`.
3. The text is returned to the agent as the tool result and becomes part of the conversation.
4. The agent decides the next command (`click @e3`, `fill @e5 "tent"`, ...).

Token costs: no browser tool definitions to load (it uses the Bash tool that every agent already has); a snapshot is returned **only when the agent asks for one**; the agent must know the command syntax, and a wrong command costs a call plus the error text.

**Approach B: Playwright MCP**

1. The agent first loads the tool definitions (names, descriptions, JSON schemas) of the Playwright MCP tools. In this benchmark that is one ToolSearch call. The definitions then stay in the context for the rest of the run.
2. The agent calls a tool, for example `browser_click` with an element reference.
3. The MCP server runs the action with Playwright and returns text. For most actions the result includes a **snapshot of the page after the action**, so the agent sees the new state without asking.
4. The agent reads it and decides the next tool call.

Token costs: the one-time loading of definitions and their presence in every later model call; a snapshot added to the context after most actions, whether or not the agent needed it; in exchange, fewer explicit "look at the page" calls and no command-syntax errors.

**Approaches A and B, common final part: wick-ag-lens**

1. The agent assembles one command with the 15 `--step` arguments and the 30 audits.
2. It runs the command through the Bash tool, redirecting the JSON to a file (about 430 KB). The agent never prints it.
3. wick-ag-lens opens its **own** browser (not the one the agent used), signs in, performs the steps, audits the page after load and after every step, and writes the file. No tokens are spent during this.
4. The agent runs a short script that prints a compact per-step summary, reads it, and writes the final table.

Only the compact summary reaches the model. If the agent had printed the whole JSON, it would have cost on the order of 100,000+ tokens in a single result, which is why the prompt forbids it.

### A.4 Where the difference between A and B can come from

| Source of tokens | A: agent-browser | B: Playwright MCP |
|---|---|---|
| Tool definitions | none beyond the standard Bash tool | Playwright MCP definitions loaded once, re-read on every later call |
| Page snapshots | only when requested; interactive elements only | returned after most actions; format and size set by the MCP server |
| Command or call errors | possible (syntax, wrong selector); each costs a call plus error text | possible (wrong reference); each costs a call |
| Session handoff to wick-ag-lens | extra calls: `state save`, then `-a <file>` | none: credentials are passed to wick-ag-lens |
| Agent's own reasoning and writing | same | same |
| wick-ag-lens run and summary | same | same |

How much of the total each source contributed was **not measured**; what was measured is the split between output, cache-read and cache-write tokens (section 5.3).

### A.5 Terms

- **Snapshot:** a text description of the page (roles, names and references of its elements) that the model can read. It is not an image.
- **Tool definition / schema:** the description of a tool (its name, purpose and parameters) that must be in the model's context for the agent to be able to call it.
- **Tool call / tool use:** one request from the agent to a tool. Each one is followed by a model call that reads the result.
- **Context:** everything the model reads on a call. It grows during a run, and it is paid for as input on every call.

### C.3 What this means for the token numbers

- The JSON is about 421 KB per run, and it is about the same for A and B because both run the same journey with the same tool.
- **The JSON never enters the model's context in full**: the prompt tells the agent to write it to a file and read only a compact summary (a few lines per step). That is why the audit's size does not appear in the token totals of section 5.
- As an order of magnitude, a file of this size printed in one tool result would be roughly 123,000 tokens (assuming about 3.5 bytes per token, an estimate, not measured), more than the whole of a typical run (70,000 to 117,000 tokens). An agent that read the JSON directly would therefore cost several times more than the runs reported here, and the cost would grow with the size and complexity of the page.
- The size depends on the page and on the audits requested: more elements, more steps, more audits, a longer focus path, or screenshots (`-s`) make the file larger. Narrowing the audits (`--audits`) and the WCAG scope (`--wcag-version`, `--wcag-level`) reduces it.
